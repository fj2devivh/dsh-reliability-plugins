# @dsh-plugin/executor-gate

**执行层的「权限管理条例」。** 双区模式原先只约束了意图层（`dsh-intent-guard` 剥夺它的
write/edit），执行层却是**完全没有约束**的 —— 它一被创建就继承 `standard` 的全套能力，
可以随手改任何文件、搭任何机制、跑任意多轮实验。那正是「意图层很听话、执行层蠢」的
机制性根因：**它不是没能力，是没人管**。

本插件执行层从「默认全权」改成「**默认冻结、按任务发预算**」。

## 四条条例 → 实现

| 条例 | 实现 | 强度 |
|---|---|---|
| ① **默认冻结**（白纸开局） | 执行层 agent 被创建即套 `ctx.tools.guard()`；没有租约时一切变更类调用被拒 | **硬约束（工具层）** |
| ② **权限审批流** | 执行层 `request_permission` 申请 → 意图层 `grant_permission` 批准；或派活时把授权包写进任务书 | 工具 + 机制 |
| ③ **范围锁与时间锁** | 授权包 = 按工具的 `范围`（支持目录前缀与 glob）+ `额度`（次数）+ 时间锁；任务完成即回收 | **硬约束（每次调用都判）** |
| ④ **定律 vs 工具的边界** | `FORBIDDEN_TARGETS` 任何租约都不可授权；执行层不能给自己授权；挑战约束即记违规，三次熔断 | **硬约束** |

## 授权包长什么样

意图层派活时，把这一段放进任务书（或作为后续消息发下去）即当场生效 ——
**不需要执行层先问**：

```yaml
【授权】
任务ID: "TASK-001"
冻结定律: "THE_STRATEGY.md §5"
执行目标: "实现一人扫W，一人扫H，一人做P+W的排班逻辑"

工具预算:
  read_file:
    额度: 无限
    范围: "/data/**"
  write_file:
    额度: 5次
    范围: "/output/schedule_*.json"
  run_test:
    额度: 3次

预算外行为: "禁止。如需超出预算，必须向意图层申请。"
```

解析是**只认显式标记**的（不猜自然语言），两种写法等价：

- **结构化授权包**（上面那种，推荐）：`工具预算:` 下按工具列 `额度` / `范围`；
- **简单键值**：`允许写: A, B` / `禁止碰: C` / `写额度: 40` / `实验额度: 6`。

键名中英文都认，全角冒号与全角逗号也认（中文输入法是常态）。

### 预算是「工具 × 范围 × 次数」三元组，不是一个全局桶

三个内置预算键（`write`/`edit` 都归到 `write_file`）：

| 键 | 覆盖的调用 | 默认 |
|---|---|---|
| `read_file` | `read` / `glob` / `grep` / `read_image` 与只读 shell | 无限、不限范围 |
| `write_file` | `write` / `edit` 与变更类 shell（`Set-Content`、`Remove-Item`、`>` 重定向…） | 200 次 |
| `run_test` | 跑测试类命令（`node --test`、`vitest`、`pytest`…） | 30 次 |

**预算里没列出的工具 = 禁止使用**（「预算外行为：禁止」）。
`额度: 无限`（或 `-1`）表示次数不限，但**范围仍生效**。

范围支持两种写法，可混用：

- **目录前缀**：`/data` 或 `/data/**` → 整棵子树；
- **glob**：`/output/schedule_*.json` → 只放行匹配的文件名（`*` 不跨目录、`**` 跨目录）。

> 为什么 read 默认不限制：把读也算成「要审批」会逼意图层为每件小事开权限，
> 而读本身不改状态。要收窄就读范围/读额度显式写 —— **写默认禁止、读默认允许**，
> 这样「只加一条限制」不会意外把读能力也锁死。

### 粒度由意图层按风险定

- **探索性任务 → 宽预算**：大范围、次数给足，让它试错。
- **实现性任务 → 窄预算**：具体到文件 glob、次数给紧，防它「搞发明」。

### 预算用完 = 自动熔断 + 如实上报

额度烧满时，执行层**立刻停下**并收到一段明确的指令：报告「预算耗尽，任务未完成」，
写清 ① 已完成到哪一步（附证据）② 卡在哪、为什么不够 ③ 建议意图层怎么改预算。
**停在预算上是正确行为，不是失败** —— 要它继续就重新发一份授权包。

## 它修的两个「机制性根因」

这两条都是开发时实测抓到的，写在这里因为它们决定了实现形状：

1. **执行层不在 `agents.roots()` 里**，而 `agent/created` 是**按 scope 过滤**的
   （`dsh-agent` 的 `AgentRegistry.announce` 用 `scopeTarget(agent, agent)` 派发）——
   装在挂载点或意图层 ctx 上的监听器实测收到 **0 条**。所以执行层只能靠
   `agents.list()` **轮询发现**（`discoveryIntervalMs`，默认 1s）。
   第一版靠 `roots()` + 事件，结果是**执行层一个守卫都没装上、冻结静默失效**。

2. **折叠授权是有副作用的**，必须按消息 id 记账、每条只折一次。
   第一版每次判定都重新折叠，于是额度被反复回满（写额度 3 次，第 4 次仍放行）。
   同理，冻结时新建租约**必须保留 `foldedIds`** —— 否则那条旧授权消息下一轮又被折叠，
   当场把刚冻结的租约解冻（时间锁与熔断都因此失效过）。

## 与产品既有约定的关系（不是绕开产品）

产品给每个子 agent 的运行时常量 `SUBAGENT_DELEGATION_CONTEXT`
（`dsh-subagent/lib/types/child-agent.js`）逐字写着：

> 你是一个被委派的子 agent：**你的权限范围在启动时就固定了，无法从本会话内部扩大** ——
> 需要审批的操作会被自动拒绝。当任务需要超出该范围的访问时，**不要重试被拒的操作**；
> 在回复里说明这个限制，让委派你的 agent 来处理。

产品**有意**让子 agent 的范围在启动时固定、且拒绝**响亮地**回到子 agent，但没规定
「固定成什么」—— 那一格是空的。本插件把「启动时的范围」默认设成**空**（冻结），
并给出唯一一条合法的扩权路径。

> ⚠️ 一处**如实标注**的取舍：上面那句常量说「无法从本会话内部扩大」，而本插件的
> `grant_permission` 由**意图层**发起、能中途改租约。这是刻意的：用户要的就是
> 「申请 → 审批」这条流。产品那句约束的真实意图是「**子 agent 自己**不能扩权」——
> 那一条被严格实现了：执行层调 `grant_permission` 会被响亮拒绝并记违规。
> 子 agent 能自己触达的只有 `request_permission`（登记），它不放任何权。

## 边界（不假装是安全边界）

这是**工具 schema 级 + 调用级**约束，不是文件系统级安全边界：执行层仍持有 `pwsh`/`bash`。
三件事把缺口压到最小：

1. 变更类 shell 走模式匹配 + 路径提取，范围内外一律判；
2. 额度按**变更类调用**计数 —— 读、`node -v`、跑只读检查**不计数**；
3. 每个判定可落审计文件（`auditFile`，JSONL），事后逐条复核，不靠信任。

**如实标注的漏**：跑测试的**路径**不会被自动校验（命令是一整串文本，
猜「它跑的是哪个测试文件」一定会猜错）。所以机制负责「跑几次」，
「只许跑 test_01」这种收窄建议写进执行目标文字里，由执行层遵守。
要真正的隔离，得在环境层做（只读挂载 / 沙箱 write 目录），不在本插件范围内。

## 配置

```yaml
- id: executor-gate
  name: '<ENTRY_URL>'                     # build-presets.mjs 自动填
  config:
    enabled: true                         # 总开关（关掉 = 执行层恢复全权）
    presetId: dual                        # 必须显式传，不靠猜（猜错会去冻别的会话）
    gateSubagents: true                   # 执行层是否吃冻结
    denyIntentWrites: true                # 意图层是否也不许自己动手（与 intent-guard 同向）
    defaultWriteBudget: 200               # 首次授权没写次数时的保底
    defaultShellBudget: 30
    violationLimit: 3                     # 违规到几次熔断（连已授权范围一起收回）
    maxLeaseMs: 14400000                  # 时间锁：租约最长 4 小时
    discoveryIntervalMs: 1000             # 轮询发现执行层（理由见上文）
    logDenied: true
    auditFile: ''                         # 留空则不落盘
```

## 工具

| 工具 | 谁能用 | 作用 |
|---|---|---|
| `request_permission` | 仅执行层 | 登记申请，返回**可直接转发**的申请文本与授权包骨架 |
| `grant_permission` | 仅意图层 | 发结构化授权包（按工具的范围 + 额度 + 时间锁）。**下发后回读核对**，不一致就不报成功（见下） |
| `revoke_permission` | 仅意图层 | 立刻回收全部权限（任务完成 / 发现跑偏） |
| `lease_status` | 两者 | 查台账：各执行层的预算用量、违规、是否熔断；**外加一份「发消息可达性」名册** |

角色由 `exec.agent` 判定（运行时给的调用者），**没有任何参数能改变角色** ——
执行层无法在参数里冒用意图层身份。

## 审计层的常备租约：**它必须跑得动**（2026-09-20 修）

用户报的机制缺陷（原话）：

> 「两次独立鉴证都没能跑起来。不是它们偷懒 —— **审计层在您这台机器上压根没有
>  「允许跑程序」的权限**（两次都是它自己用台账查实并原文报回来的）。」
> 「**现在的审计层没办法审计**」

**根因**：审计员也是 `origin === 'subagent'`，所以它**照样吃执行层的默认冻结** ——
而冻结态只放行"只读类命令"，`pytest` / `node --test`（`run_test`）与 `python -c`、
任何重定向（`write_file`）都会被判「没有这个工具的预算」。
**审计的本来工作就是跑验收** —— 于是它一步都动不了，只能如实回一句"我没权限跑程序"
（它没撒谎，是机制把它堵死了）。

**修法**：权限门**按能力认出审计层**，给它一张**常备租约**。

| | 执行层 | **审计层** |
|---|---|---|
| 怎么认出来 | `origin === 'subagent'` | 同上 **＋ 工具面具里没有 `write`/`edit`** |
| 读 | 按预算 | **无限** |
| 跑测试 / 跑命令 | 要授权 | **有额度**（`auditShellBudget`，默认 40 次） |
| 写 | 要授权（按范围） | **只许 `_audit_scratch/`**（`auditWriteBudget` 次） |
| 产品树 | 按授权范围 | **写不了**（不在写范围里） |
| `notes/_endstate`（台账 / 终局定义 / 鉴证报告） | 受范围约束 | **显式进黑名单** —— 改不了卷子 |

判据刻意**按能力认，不按名字或人格猜**：审计员的 `write`/`edit` 是被预设的
`toolFilter.deny` 拿掉的，所以"它写不了东西"是**结构性、可观测**的事实。
判不出来（拿不到工具视图）就**按普通执行层处理**（不猜）。

三处工程细节（都是踩出来的）：

1. **判据在每次调用时重算**，不在装守卫那一刻定死 —— 子会话的工具面具是在**创建窗口**里
   装上的，轮询到它时可能还没装完；定死就会把审计层误判成普通执行层（**那正是这次事故的形状**）。
2. **显式授权永远优先**：意图层真的给它发过授权包，就不再塞系统默认租约。
3. 顺手补了两个**真洞**（给审计层发租约时实测出来的）：
   - `> private_app/out.txt` 这种**裸相对路径**以前一个候选都抽不到 ⇒ 范围检查等于没做；
   - `python -c "print(1)"` 里的 `print(1)` 被当成写目标 ⇒ 假警（**假警会把真警一起淹掉**）。
   现在：重定向/写类 cmdlet 的目标**点名抓**，候选只留"像路径"的（有分隔符或有扩展名）。

`auditLease: false` 可以关掉这一路（那时审计层与执行层一样白纸开局，必须由意图层授权）。

## 只读地打开 ≠ 改写它：**按代码里到底有没有写判**（2026-09-20 修）

用户报的机制缺陷（原话）：

> 「用「读」类工具去拿它 ⇒ 放行；用 Python 去打开它 ⇒ 整条命令被拒，理由是「路径不在允许范围内」。
> 它现在分不清「只读地打开」和「改写它」，这是它的一处设计缺陷。」

**根因**：`SHELL_WRITE_PATTERN` 里有 `python -c` / `node -e`（本意是防"用内联代码绕过写闸"），
但那条规则命中的是**整条命令**，下一步就按「命令里出现过哪个路径」去查写范围。
审计层的写范围只有 `_audit_scratch/`，于是只要代码里提到别的路径，整条命令就被判越权 ——
**40 次跑测试的额度因此一次都花不出去**。

**修法**（就是用户给的那条 甲/乙里的做法）：**看代码里到底有没有写/执行的动作**，不看命令里出现了哪个路径。

| 命令 | 以前 | 现在 |
|---|---|---|
| `python -c "print(open('notes/x.md').read())"` | 变更类 ⇒ 查写范围 ⇒ **拒** | **只读档 ⇒ 放行**（同「读文件」，不查写范围、不计数） |
| `python -c "print(1 if 2>1 else 0, 8>>1)"` | 引号里的 `>` 被当重定向 ⇒ 变更类 | **只读**（引号里的 `>` 是 Python 运算符，不是 shell 重定向） |
| `python -c "open('private_app/x','w').write('y')"` | 变更类，但**一个目标都抽不出来** ⇒ 白放行 | 变更类 + **目标抓得到** ⇒ 照旧查范围、扣额度 |
| `python -c "p='private_app/x'; open(p,'w')"` | 同上（免检写入） | **拒**：有写动作却解析不出字面路径，证明不了在范围内 |
| `python -c "…" > out.txt` | 变更类 | 变更类（重定向在引号**外**，照旧算写） |
| `pwsh -Command "Remove-Item x"` | 变更类 | 变更类（**内联只读这一档绝不放 `pwsh -Command`**） |

判据的四条（写在 `isReadOnlyInline` 上方，不留暗门）：
引号外没有变更信号（摘掉 `python -c` 这一小段后再测，否则它自己就命中写模式）；
解释器只收 `python` / `py` / `node` / `deno` / `perl` / `ruby`；引号配对；代码里不出现任何写/执行动作
（`open(…,'w')`、`.write(`、`os.remove`、`shutil`、`subprocess`、`eval`/`exec`、`writeFileSync`、联网工具…）。

⚠️ 顺带关掉的**真洞**：以前 `python -c` 里的写**没有目标可查**（既没重定向也不是写类 cmdlet），
所以"用 python 往产品树里写"其实不受范围锁约束。现在代码里字面写出来的路径会被抓成写目标；
解析不出来的，**拒**（并把三种改法写进拒绝话术：写死路径 / 用 `Set-Content` / 把代码写成夹具脚本再跑）。

如实标注边界：文本判据**挡不住刻意混淆**（`getattr(os,'sys'+'tem')`）——
这一档要的是"挡掉误杀、且不给出明显的绕法"，不是"证明代码只读"。真正的只读只能靠环境层。
`python 脚本.py` 同理：脚本里写什么，命令文本里看不见，靠额度与事后审计（这条边界早就写在上面）。

> 配套的一条：`dsh-knowledge-gate` 里审计层**免过操作闸**（`exemptAudit`，默认开）——
> 它的授权来自任务书里的验收标准，而且 `dispatch_audit` 本身就在闸里（意图层没确认过就派不出审计）。
> 它照样收到那份资料块，只是不因没确认而被拒。

## 两处「确认在骗人」的修法（2026-09-19 用户实测反馈）

两条症状是**同一类**：回执说的是"我做了什么"，不是"现在是什么"。

### ① 授权回读核对：`grant_permission` 不再"发完就报成功"

用户的原话：

> 「症状：grant_permission 回「已授权」、打印预算、打印写范围 —— 而实际生效的是
>  read_file 1/1、写范围空。**六个执行层被拒写**。」

修法三件：

1. **回读**：写完租约之后，用**与执行层守卫同源**的那条路（`leaseFor` = `resolveLease`）
   把租约**读回来**；
2. **核对**（`verifyGrant`，纯函数）：逐项比「你要的」与「实际生效的」——
   写范围（少一条也算）、每个工具的额度、禁止碰、任务 id、时间锁、以及**是否冻结**；
3. **不一致就不打印成功框**：回执变成 `❌ 授权没有生效` + **实际生效值** + **对不上的地方** +
   下一步（查台账 / 重发 / 把授权写进任务书）。核对结果另记一条审计（`grant_verify`），
   事后可查"这一次是真生效了，还是只有回执漂亮"。

⚠️ 一条踩过的坑写在函数注释里：比较的两边都得是**归一化之后**的路径
（折叠时 `normalizePath` 会把 `D:/proj/src` 折成 `d:/proj/src`，拿原样比会报"少了 D"这种假警 ——
**假警会把真警一起淹掉**）。

### ② 发消息前查活：`send_message` 不再把"写进队列"说成"已送达"

用户的原话：

> 「症状：给已经收工的执行层发消息 ⇒ 回「已送达」，实际没人会读。
>  修法：发送前查活；返回三态之一 —— **排队中 ／ 已拒绝（原因）／ 建议新建会话**。」

判据按**产品的真实语义**（读了 `dsh-subagent` 的 `sendMessage` / `coldResume` 源码）：

| 目标的状态 | 三态 | 为什么 |
|---|---|---|
| 活着（在跑或空闲） | **排队中** | 在跑就插进去，空闲就开一轮 —— 消息会被读到 |
| 不在活着，但 `mode === 'continuable'` | **排队中（会冷启动一轮）** | 产品会 `coldResume` 把它唤醒 |
| 不在活着，且 `mode === 'one-shot'` | **建议新建会话** | 产品直接回 `NOT_RESUMABLE`（叫不醒） |
| 名册里没有这个 id | **已拒绝（原因）** | id 写错了，或那不是你的直接子会话 |

拒绝话术里明写：「**「已送达」这三个字只对活着的目标成立**：对已经收工的会话，
写进队列等于写进垃圾桶」，并给出出路（重新派 / 派审计 / 写台账）。
`lease_status` 里也加了同一份**发消息可达性名册**，所以发之前就能查。

> ⚠️ 实现上有一条硬约束：名册（`subagents.listChildren`）是**异步**接口，
> 而 `tools.guard` 是**同步**判据（返回 Promise 会被当成"拒绝"）。
> 所以名册由定时器（`catalogIntervalMs`）刷进缓存、guard 只读缓存；
> 而"它现在活着吗"那一条始终是**实时**判的（`agents.list()`）。

### 为什么需要**两个**回归 —— 这不是重复

`smoke.mjs` 里的 `tools` 是**替身**（真 `dsh-tools` 需要整条 preset 运行时）。
替身的问题是：**"真实现会抛、替身不抛"的差异，在 smoke 里永远看不到。**
本插件就因此藏过一个**会让主路径整体失效**的缺陷：

> 第一版在**每个 agent 的 scoped ctx** 上各注册一遍四个工具。真 `ToolRuntime.register()`
> 用 `NamedEntries` 去重 —— **同名的工具在同一个层里只能注册一次**，第二次抛
> `tool "X" is already registered`。生产表现：**意图层拿得到 `request_permission`，
> 而每个执行层都拿不到**，于是"执行层申请权限"这条主路径整体失效。
> 而 smoke 当时是全绿的，因为替身不去重。

所以 `_verify-tool-register.mjs` 把**真依赖从 `app.asar` 解出来接上**（`_stage/probe/`），
用真 `Context` + 真 `ToolRuntime` 验两件只有真依赖能验的事：

1. **手写定义真 `register()` 收不收** —— 拒收就抛错，而 apply 阶段抛错会让
   **整个窗口/会话起不来**（`dsh-executor-loop` 那次手写 `Config` 的事故）；
2. **`tools.guard()` 是否真的只对该 agent 生效** —— 整套设计全压在这条前提上：
   如果它其实是全局的，**冻结一个执行层就等于冻结所有人**（`dsh-intent-guard`
   记录过的生产事故）。判据是真 `execute()` 端到端：装了守卫的 agent 被拒、
   没装的照常跑出 `PROBE_RAN`。

它跑之前需要真依赖在位（解包约 28 MB）。**注意：现在别删它了** ——
从 2026-09-19 起这条校验是**总闸门 `verify-all.mjs` 的一项**，删了之后
`node verify-all.mjs` 会红（表现为"缺依赖"而不是"插件坏了"）。真要重建：

```powershell
node "D:\<dsh-plugin-root>\插件\_tools\asar-dump.mjs" `
  "D:/<dsh-plugin-root>/DSH Desktop/resources/app.asar" `
  "node_modules/@deepseek-ai" `
  "D:\<dsh-plugin-root>\插件\_stage\probe\node_modules\@deepseek-ai"
```

### 它第 4 节直接对着「会不会把桌面端搞坏」那一步

本项目最惨的一次事故是：`dsh-executor-loop` 导出了一个**手写的 `Config` 描述对象**，
而 Cordis 的 `resolveConfig()` 会读 `runtime.Config['~standard'].validate(config)` ——
手写对象没有 `~standard`，于是 `undefined.validate` 抛 TypeError，
**整棵插件树加载失败、DSH Desktop 直接打不开**。

所以第 4 节把那条路**逐字复刻并真跑**（`resolveConfig` 只有 7 行，出处
`@deepseek-ai/cordis/lib/index.js:955-961`）：

1. 用 preset 里那个**真 `file://` URL** 动态 import 两个插件；
2. 对两个模块都调 `resolveConfig()`，断言**不抛**（= 没有非 Standard Schema 的 Config）；
3. 在真 `Context` 里真挂载两个插件，断言 fiber 到达 **ACTIVE(=2)** ——
   不是 `PENDING`（依赖没满足、apply 从未执行），也不是 `FAILED`（apply 抛错把窗口带下去）；
4. 断言两个插件都没往 `logger.error` 写东西。

> 这三条合起来才是"能 import ≠ 能挂上"那句话的完整答案 ——
> 本项目的教训原文是：**配置解析发生在更早、而且是硬失败**，
> 所以任何改动都要有「模拟真实加载路径」的预检，只跑单元测试不够。

### 还有一个**结构性**取舍，也是实测改出来的

取 `tools` 服务用的是 `ctx.get('tools')`，**不是 `ctx.tools`**：
Cordis 对「没在 `inject` 里声明就取服务**属性**」是**抛错**的
（`cannot get property "tools" without inject`），而 apply 阶段抛错会让
**整个 fiber FAILED** —— 权限门静默失效。实测踩过：加了挂载点注册之后
fiber 直接变 `3 (FAILED)`，smoke 里"冻结态 write 被拒"一整片全红。

为什么也不 `inject: ['tools']`：那样服务不可用时插件会**永不挂载**（连冻结都没有），
比"少一批工具"严重得多。`ctx.get()` 取不到只是 `undefined`，能告警而不影响挂载 ——
与 `dsh-intent-guard` 取 `agentPresets` 的取舍一致。

### smoke 里 `tools` 替身照抄了哪些真语义

替身**不只是"有个 register"**，它复刻了真实现的三条会咬人的规则：

| 语义 | 为什么必须复刻 |
|---|---|
| `register()` **同名去重并抛错** | 就是上面那个主路径失效的缺陷 |
| `guard()` **单调**、首个返回字符串者即拒绝 | 判据不能是"我的规则我说了算" |
| 有 scope 落该 scope、无 scope 落全局 | 混淆这两者会让"误伤所有人"看起来像正常 |

> 顺带一条教训：`subagent` 的 `agent/created` 事件是**按 scope 过滤**的
>（`dsh-agent` 用 `scopeTarget(agent, agent)` 派发），装在挂载点或意图层 ctx 上的
> 监听器实测收到 **0 条**。所以执行层只能靠 `agents.list()` 轮询发现 ——
> 这个事实同样是**真依赖实测**出来的，替身里那种"事件一定会到"的假设会骗人。

## 两条硬要求（都有事故背景）

1. **`apply` 绝不抛错。** 2026-09-15 01:01 事故：插件在 apply 阶段抛错会让
   **整个窗口/会话起不来**。这里每一步都 try/catch，失败只告警不断线。
2. **不导出 `Config` schema。** `dsh-executor-loop` 的事故：手写的 `Config` 不是
   Standard Schema，`resolveConfig()` 读 `~standard` 抛 TypeError，
   **整棵插件树加载失败、DSH 打不开**。这里用 `normalize()` 逐字段校验，零跨包依赖。

## ⚠️ 已修的生产故障：手写工具定义漏了 `type: 'object'`

**症状**（2026-09-18 实测）：双区「**能打开，但没法工作**」——
意图层收到用户第一条消息后，**第一个 step 就 `turn/end` 报错，一句话都没说出来**，
于是从没派活给执行层，执行层也就从未出现。

**报错原文**（会话日志里查得到）：

```
Invalid schema for function 'grant_permission':
schema must be a JSON Schema of 'type: "object"', got 'type: null'.
```

**根因**：本插件的四个工具是**手写 definition**（没走 `defineTool()`）。
真 `defineTool()` 内部会调 `parameterSchemaSpecToJsonSchema()`，把「每字段一条」的
参数 DSL 编译成 `{ type: 'object', properties: {...}, required: [...] }`；
而我当时把 `parameters` 直接写成了**裸的 properties 映射**，漏了 `type: 'object'` 那一层。
模型 provider 校验工具 schema 时直接 400 拒掉**整个请求**，那一轮连模型都没跑起来。

**修法**：新增 `compileParameters()`，逐字对齐真实现的产物形状
（`type: 'object'` + `properties` + 仅在有必填项时才出现的 `required`）。

### 为什么当时三道离线回归全是绿的（这条教训比 bug 本身重要）

**真 `ToolRuntime.register()` 根本不看 `parameters`。** 它只做：

```js
assertSupportedJsonSchema(output.schema)   // ← 只校验 output，完全不碰 parameters
```

所以「register 收下了」**完全不代表**「能发给模型」。
而我当时的校验脚本恰好只验到「register 没抛错」就收工了 ——
**判据停在了错误的深度**，这才是真正的漏洞。

**补上的判据**（两处，都是看「交出去的东西长什么样」，而不是「有没有抛错」）：

| 位置 | 断言 |
|---|---|
| `_verify-tool-register.mjs`（真依赖） | 真 `tools.schemas()` 里每个工具的 `parameters.type === 'object'` |
| `smoke.mjs`（替身） | 每个 definition 的 `parameters.type === 'object'`，且 `required` 都真在 `properties` 里 |

`schemas()` 是**真正会发给 provider 的那份投影**，所以它才是覆盖这次故障的正确深度。

> 顺带一条纪律：**「真 import 成功」与「真能挂上」是两件事**
> （`executor-loop` 的教训）；这次又加一条 ——
> **「能挂上」与「能发给模型」也是两件事**。每加一层，判据就得跟着往深走一层。

## ⚠️ 两处已修的「闸门诚信」缺陷（2026-09-18 用户实测反馈）

用户把要害概括得很准：**「我要修的只有一件事：台账要跟我发出去的那份授权对得上。」**
下面两条都不是「闸太紧」，而是**闸的读数不可信 / 覆盖面不一致** ——
那比闸太紧危险得多，因为前者浪费往返，后者是真放行。

### ① 台账与授权对不上：「我授权了，它却被当成没授权」

**症状**：意图层调 `grant_permission`，拿到**看起来完全正常**的回执
（任务名、范围、时间锁都写在里面），但执行层那边查台账是
「任务未命名 / 冻结 / 无任何工具预算」。

**根因（两个叠加）**：

1. **`lease_status` 走了与判定不同的路。** guard 判定走 `resolveLease()`
   （会把会话日志里的授权折进租约），而台账当时**直接读 `ledger.leases` 的原始条目** ——
   那条目可能只是「尚未结算的模板」。两条路读数不一致 ⇒ 台账撒谎。
   **修法**：台账改用 `adapter.leaseFor()`（= 同一个 `resolveLease`）。
   **判据必须与判定同源** —— 这是本次最要紧的一条教训。
2. **冻结模板会盖掉已折好的租约。** 守卫晚装时无条件 `ledger.leases.set(冻结模板)`，
   把先到的授权抹掉。**修法**：只在 `grantCount === 0` 时才写模板。

**顺带加的护栏**：`grant_permission` 现在会检查目标 id **是否真的是活着的执行层**，
不是就当场告警并列出真实 id —— 「id 写错」是这条症状最常见的成因，
而它最坏的地方在于**回执照样漂亮**（看起来成功了）。

另外：**意图层在台账里不再被显示成「冻结 / 无预算」**。
它本来就不持有租约（那是角色属性，不是冻结），照模板显示会让人误以为闸门坏了。
台账现在按「意图层（不持有租约；write/edit 被 intent-guard 直接剥夺）」如实说明。

### ② 覆盖面不一致：「我以为是闸的东西，有的会话根本没上闸」

**症状**：某个会话在收到任何授权之前就把文件写进去了，而且是它自己如实报的。

**根因**：`watch()` 里有一行一次性判定 ——

```js
if (presetOf(agent) !== ownPresetId) return   // 失败即永久放弃
```

子会话的 preset 归属是在**创建窗口内**才建立起来的（产品先让子 join 父的 preset、
再装它自己的 persona 与工具限制）。轮询若早了一拍，`composedPreset(childCtx)`
返回 `undefined`，这个执行层就被**永久漏掉**。这与 `dsh-intent-guard` 当年的生产事故
是**同一个形状** —— 它靠重试修好，而我的轮询没有重试。

**修法（三件，缺一不可）**：

1. `watch()` 不再「一次判不是就放弃」：归属还没建立起来的先记入**待重试队列**；
   `discover()` 每轮先补判一遍，超过 `identityRetries` 才放弃**并留 warn**。
2. **把 `discover()` 里那行自己先 `continue` 的判定删掉** —— 它把上面的重试整条短路了
   （第一版加了重试却根本走不到，属于同一个 bug 的第二层）。
3. 新增**覆盖面审计**（`coverageAuditMs`，默认 5s）：凡是「进过名册但守卫没装上」的
   执行层，按 `COVERAGE GAP` 点名到具体会话 id；`agents.list` 不可用时**响亮告警**
   （它是执行层唯一的发现路径，静默返回空 = 全部裸奔）。

**如实标注一个消除不掉的窗口**：守卫只能装到**已经存在**的 agent 的 scoped ctx 上，
所以子会话从**被创建**到**被冻结**之间那一段（默认 <1s）它确实是裸的。
这段窗口没法从根上消掉，但**绝不允许静默** —— 现在它会出现在日志里
（`COVERAGE GAP`），而不是靠事后猜。

### 回归怎么钉住的

`smoke.mjs` 新增两组断言（「台账必须与授权一致」/「覆盖面」）：

| 断言 | 防的是什么 |
|---|---|
| 授权后台账立刻显示**已授权 + 任务名 + 按工具预算** | ① 的直接复现 |
| 用掉一次后台账显示 `1/4`（记账 = 真实用量） | 台账沦为摆设 |
| 按 `agent_id` 查与不带参数查**读数一致** | 两条查询路径给出不同答案 |
| 给不存在的 id 授权**当场告警**并列出真实 id | 「回执漂亮但没人收到」 |
| `agents.list` 不可用时**必须 warn** `UNGATED` | 静默漏掉整批执行层 |
