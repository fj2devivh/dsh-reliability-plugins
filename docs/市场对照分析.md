## 一、最相关的对子（按相关性排序）

> **这一节只是「生态位置」的取证，不是结论。**
> 每条对比后面那段「结论 / 该不该装」的建议，**请以第四节的架构口径为准** ——
> 那里有两条建议被推翻（`dsh-gungnir` 与目标可视化都不需要）。

### ① executor-loop ↔ `yunxiyang/dsh-loop-continue`（36 分，同类目）

> 市场描述：「续跑『叙述了下一步动作却没调用工具』就结束的 agent 轮次：插件在
> `agent/turn-stopping` 回放该轮日志，让**裁判模型**回答一次 true/false，命中的话
> 把同一轮再推进一步。」

**相同点**：都针对「agent 停得太早、活没干完」。都用 `turn-stopping` 这个钩子。

**关键差异 —— 机制与代价完全不同**：

| | executor-loop（我们） | dsh-loop-continue（市场） |
|---|---|---|
| 触发判据 | **状态判据**：goal 是否已完成 / disarmed / agent 是否 idle | **语义判据**：回放日志，问裁判模型 true/false |
| 每次判断的 token 成本 | **0**（纯宿主侧状态机） | **每轮一次 LLM 调用** |
| 时间尺度 | **跨轮、跨会话、跨进程重启**（goal 落盘 + 断锚重新武装） | **单轮之内**（把同一轮再推一步） |
| 抖动风险 | 靠 `maxTokensPerTask` / 看门狗 / `autoResume` 护栏 | 靠裁判模型的判断质量 |

**结论**：这不是重复，是**不同层次**。市场那个解决「这一轮话没说完就停了」，
我们那个解决「会话断了 / 压缩了 / 进程重启了，目标还在不在」。
两者**可以同时装**（一个管轮内，一个管会话级），但要注意别都去抢 `turn-stopping`。

**我们的独特处（描述层面看市场没有）**：goal 的**持久化续行** —— 会话恢复或 fork 后
goal 被 disarm 时自动重新武装。市场那份描述只讲轮内。

---

### ② executor-loop ↔ `Jonah-Wu23/dsh-gungnir`（50 分，**最高分**）

> 市场描述：「证据驱动目标校验插件。通过 `/ultragoal` 锁定目标，并依据**命令退出码与
> 生成产物**验证完成状态，防止模型虚报任务完成。」

**同一个问题的两种解法**：都在防「模型虚报完成」。

| | executor-loop | dsh-gungnir |
|---|---|---|
| 防虚报的手段 | 看 goal 状态 + 空闲就补推 + 按锚点文件定目标 | **独立验证产物**：跑命令、看退出码、检查文件 |
| 依赖 | 锚点文件（STAND.md/GOAL.md…）+ goal 服务 | 用户先 `/ultragoal` 锁目标 |
| 强度 | 中（「你没停我就推你」） | **强**（「你说完了，我验一遍」） |

**结论**：**它们在能力上是互补的，而 gungnir 那一半我们确实没有。**
`noStopPolicy` 只保证「不停」，不保证「做对了」。
如果要补一块，**补「独立验证产物」比再加续行逻辑更值** —— 但那是 gungnir 已经在做的事，
先用它比自己写更划算。

---

### ③ executor-loop ↔ `KarlOfLaw/dsh-goal-mode-enhance`（24 分）

> 市场描述：「composer 上方的目标栏支持创建、多行编辑、暂停、恢复、完成与清除并实时
> 显示轮次进度，工具行入口带阶段色点，设置页提供目标总览。」

**同一个 goal 对象的两个面**：这是 **UI 面**（人看/人操作 goal），我们是**执行面**
（宿主自动推进 goal）。它做的是「可视化与手动控制」，我们做的是「自动重新武装与续行」。

**差异点很重要**：它能「恢复」暂停的 goal —— 那是**人**点一下恢复；
我们的 `resumePausedGoals: false` 是刻意**不碰**人暂停的 goal（尊重人的优先权）。
两条设计并不冲突，甚至是同一套价值观的两个实现。

**结论**：**高度互补，建议共存。** 装了它，你能看见 executor-loop 在推哪个 goal。

---

### ④ executor-loop ↔ `dsh-answer-reviewer`(16) / `CAI-MH/dsh-quality-review`(16)

都是「独立 LLM 审查每轮输出，不达标就引导 agent 修复」。
与我们的 `steerWhenReady`（空闲时补一条 steering 消息把 agent 推回执行前沿）**形似**，
但它们的判据是**回答质量分数**，我们的是**目标是否还在推进**。
同样是「轮级」vs「会话级」的区别。

---

### ⑤ executor-view ↔ `Mombrane/dsh-subagent-monitor`（40 分，**几乎正面撞车**）

> 市场描述：「Web UI 子代理实时监视面板：侧边栏底部入口 + 右上角常驻卡片面板，实时展示
> 当前会话每个子代理的运行状态（运行中/耗时/终态）、**树形缩进**，一键跳转子代理会话并
> 支持返回主会话，刷新自恢复、移动端默认隐藏。」

这一条对我们的 `executor-view` 是**实质性重叠** —— 子代理列表、状态、耗时、跳转全都有。

**我们多的**：`token` 累计（四桶求和）、活跃轮次耗时（`subagentTiming`）、
以及把它做成**键控 tab 席位**（`sidebar.right.pane.tab`）而不是覆盖式面板。

**它们多的**：移动端适配、刷新自恢复、侧边栏底部独立入口。

**同生态的还有一批**（说明这块很挤）：

- `xyAxzy/dsh-conversation-map` —— 全工作区会话树状图，**明确标了「子代理谱系」**
- `miuzel/dsh-subagent-ui` —— 子代理搜索、监控、**打断**、批量归档
- `aa2246740/dsh-watcher` —— 只读观察器：阶段数/执行数/耗时/**tok/s**/并行分支
- `Fayelin12/dsh-office`、`lihang-lh/dsh-task-panel`、`Iwctwbh/dsh-flowglass`、
  `kk112222/dsh-chat-index` 等也都在列子代理/子会话

**结论**：**右侧栏「列出子代理」这件事，市场里至少有 5~8 个成熟实现，其中
`dsh-subagent-monitor` 与我们的重合度最高。** `executor-view` 是我们三个里**最容易被替代**的一个。
它唯一的差异化是「token + 活跃耗时」这两列数字，以及不覆盖随包 UI 的席位注册方式。

### ⑥ intent-guard ↔ 市场里**找不到正面对手**

按「只读 / 不能修改 / 工具掩码 / 禁用工具 / 沙箱」等词扫了全表 601 条，
**没有一条是「在工具 schema 层面剥夺 write/edit」的**。最接近的三条都不对症：

| 市场插件 | 它的做法 | 为什么不同 |
|---|---|---|
| `SiriLee/dsh-approval-hotkeys` | 审批面板上 Enter 确认 / Esc 取消 | 是**审批层的快捷键**，不剥夺任何工具 |
| `hyzyn/dsh-plugin-kit#docker` | Docker 面板默认只读，启停删需显式开权限 | 是**某个面板自己的只读**，不是 agent 工具集 |
| `tomowang/dsh-tui` | 终端客户端里的权限/计划管理 | 是**客户端功能**，不是工具约束 |

**结论**：**intent-guard 是这三个里设计最独特的一个。**
它剥夺的是**工具 schema 本身**（模型连「能改文件」这个选项都看不见），
而不是「改的时候弹个确认框」。这在市场 601 条描述里找不到同类。

> 诚实补一句：这**不等于**「市场上没有」。可能有插件做了但描述没这么写。
> 要确认得逐个读源码，本报告只到描述层面。

## 二、生态合规性：一个真实的差距

市场列表的**收录门槛**（原文）是：

> 「本列表收录可通过 `dsh plugin add` 安装的社区插件（**均声明了 `dsh.bundle` manifest**）」

实测我们三个插件的 manifest：

| 插件 | `dsh.bundle` | `dsh.client` | `private` |
|---|---|---|---|
| `dsh-executor-loop` | ❌ 无 | ❌ 无 | `true` |
| `dsh-executor-view` | ❌ 无 | ✅ **有**（`platform: web` + 3 个 inject） | `true` |
| `dsh-intent-guard` | ❌ 无 | ❌ 无 | `true` |

**解读**：

- 三个都**进不了**市场（没有 `dsh.bundle`），也**不能被 `dsh plugin add` 安装** ——
  它们是靠自定义 profile 补丁层 + `install-linked-plugins.mjs` 装的。
- 但 `dsh-executor-view` **声明了 `dsh.client`** —— 那是**官方约定的客户端插件形态**，
  说明它的接法是对的（`dsh-client-modules` 正是扫这个字段）。
- **差距的性质**：不是「做错了」，而是「**没走生态的门**」。要让它们能被一键安装、
  能被别人用，需要补 `dsh.bundle`（一个指向 `cordis.patch.yml` 的清单）+ 发布到 npm。

**这个差距值不值得补，取决于你想不想让别人用。** 自用的话，现在这套（包名 + 链接）更省事。

## 三、总体判断

### 相关性分布

| 我们的插件 | 市场里的对应数量 | 最接近的 | 重叠程度 |
|---|---|---|---|
| `executor-loop` | 同类目 4~6 个 | `dsh-gungnir`(50) / `dsh-loop-continue`(36) | **中**（不同层次，部分互补） |
| `executor-view` | 至少 5~8 个 | `Mombrane/dsh-subagent-monitor`(40) | **高**（最容易被打平） |
| `intent-guard` | **0 个对症** | 无 | **低**（描述层面看是空白） |

### 那我们做的东西价值在哪

三条具体的、描述层面站得住的差异化：

1. **executor-loop 的「零 token + 跨进程持久」组合** ——
   市场同类都是「每轮花一次 LLM 调用」的语义判断；我们是纯宿主状态机，
   且管的是 goal 在**会话重启后**还在不在。这个组合我没在描述里看到第二家。
2. **intent-guard 的约束层级** —— 剥夺 schema vs 弹窗确认，是两个强度。
   「意图层物理上看不见写工具」这条路，市场里没找到同类。
3. **executor-view 的 token/耗时两列 + 键控席位** —— 差异化最薄，
   但「不覆盖随包 UI」这个接法是对的。

## 四、按**架构口径**重判（这一节才是结论）

前三节是「市场重叠度」口径，**用于了解自己在生态里的位置是有效的，用于决定该做什么是错的**。
正确的口径是：**这套东西是一个分层架构，要看的是「缺哪个部件」，而不是「哪个插件更强」。**

### 它的分工

```
意图层（dual 预设）   理解意图 → 定规格（目标/范围/验收标准/证据要求）→ 亲自验收
    │  ↑ intent-guard 在这里：剥夺 write/edit，让「不动手」成为硬约束
    ↓
执行层（subagent）    只认规格做实现 → 交证据不交结论
    ↑  executor-loop 在这里：goal 持久化、断档重新武装、空闲补推
    ↑  executor-view 在这里：观测（列出执行层子会话）
```

### 按这个口径，逐条重判

| 市场插件 | 我原来的说法 | 重判 |
|---|---|---|
| `dsh-gungnir`（证据驱动目标校验） | 「能力缺口，该装」 | **不需要。** 那是**意图层的本职** —— 文档里写死了「执行层回报『做完了』**不是证据**，你必须亲自读产物、亲自跑验收命令」。再装一个验证插件 = 在层内又套一层，还会把「谁负责验收」搞糊 |
| `dsh-goal-mode-enhance`（目标可视化） | 「缺可视化，该装」 | **不需要。** 一个会话推一个 goal，「在推哪个」这个问题本身不成立。目标怎么细分是实现细节。装了只是多一块要看的 UI |
| `dsh-loop-continue`（轮内续跑） | 「不同层次，可互补」 | **不需要。** `executor-loop` 的 `steerWhenReady` 已经覆盖同一症状，且**零额外 LLM 调用**（市场那个每轮烧一次裁判模型）。日志里实测触发过：`continuation steered to session session-771231fa…` |
| `dsh-subagent-monitor`（子代理面板） | 「红海，不值得重造」 | **无所谓。** 已经实现了、能用，收工。自用不计较「有没有更好的」 |

### 结论：三个部件，没有缺口

| 部件 | 角色 | 状态 |
|---|---|---|
| `intent-guard` | **承重墙** —— 没有它，「意图层」就只是一段人格提示词 | 已完成、已验证 |
| `executor-loop` | **驱动** —— goal 的持久化与续行 | 已完成、已验证 |
| `executor-view` | **观测** —— 够用就行 | 已完成、已验证 |
| 验收 | **意图层的职责**，不是插件 | 无需新增 |
| 目标可视化 | **伪需求** | 无需新增 |

### 关于「不上传」

前三节列的那条「生态合规性差距」（没有 `dsh.bundle`、进不了市场），**既然是自用，就不成立** ——
而且现在的做法是**对的**：

- 补丁层是**有意的本地改动**，不是给别人分发的包。
- 硬套成 `dsh plugin add` 反而更糟：等于让 `dsh plugin` 去管一个你正在反复改的本地目录，
  还要多一层 npm 发布的包袱。
- 真正值钱的运维资产（`verify-all.mjs`、闸门、快照）**本来就不该上传** ——
  它们是针对这台机器、这个 DSH 版本的，换个环境就是废纸。

### 一条必须记住的边界（不是缺口，是已知取舍）

意图层的验收是**软的**（人格提示词驱动），而 `intent-guard` 锁 write/edit 是**硬的**。
这个组合是**有意的**：约束靠工具层硬锁，验证靠指令跟紧。
代价是「意图层验收得不够严」时没人兜底 —— 这一点 `DUAL-MODE.md` 里已经声明过，
属于**知情接受的取舍**，不是漏掉的部件。
