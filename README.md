# DSH Reliability Plugins

A 10-plugin reliability layer on top of [DeepSeek Harness](https://github.com/dataelement/dsh-desktop) (DSH) — DeepSeek's open-source, plugin-based agent runtime — that treats **unreliable LLMs as a given** and contains them with capability-level isolation instead of prompt-level politeness.

Built as my personal production system , iterated through real incidents, and validated against **601 plugins from the official ecosystem** in a mechanism-level market comparison.

> ⚠️ This is a personal production environment published in curated form. Code was generated by AI under a **design-first, verification-heavy** workflow: I own the architecture, the acceptance criteria, and the negative-control test harness; the model wrote most lines. I consider that division of labor — human judgment in, generated code out, machine-verified — to be the actual subject of this repository.

---

## The problem

Driving real projects with a multi-agent harness, I kept hitting three systemic failure classes:

| Failure class | What it looks like | Root cause |
|---|---|---|
| **Context pollution** | The intent layer reads raw source code and logs to "check" the executor, gets buried in details ("choked by construction dust"), and starts freelancing — forgetting the overall design | No separation between deciding and doing |
| **False completion** | The executor reports "done" when it isn't; nobody re-checks | No independent acceptance layer |
| **Upward pollution** | Dirty intermediate state flows into reports that reach the user / upper layers | No quarantine between field data and decision context |

These are the same problems the industry now files under *context engineering* and *agent reliability*. The difference: most products address them with better prompts. I address them by making the forbidden actions **impossible at the tool-schema level**.

## Architecture

```
                 user's words & criteria (notes/**/*.md)
                              │
                              ▼
                    ┌──────────────────┐
                    │   INTENT LAYER    │  understands, decomposes,
                    │  (dual preset)    │  defines acceptance, accepts
                    │                   │
                    │  intent-guard:    │  • no write/edit schema (can't see "modify" at all)
                    │  capability-level │  • no read/glob/grep/shell schema (can't see the site)
                    │  isolation        │  • only compass: whitelisted reports & human words
                    └────────┬─────────┘
              task book + permission lease
                             │
                             ▼
                    ┌──────────────────┐
                    │  EXECUTION LAYER  │  spawned subagent, own context
                    │                   │
                    │  executor-gate:   │  • DEFAULT-FROZEN at birth
                    │  budget leases    │  • unlocked per task: tool × scope × quota
                    │                   │  • budget burned → auto-stop, report "unfinished"
                    │  executor-loop:   │  • goal state machine persists across
                    │  0-token criteria │    sessions & process restarts
                    └────────┬─────────┘
                             │ dispatch_audit (black-box)
                             ▼
        ┌─────────────────────────────────────────────┐
        │  AUDIT LAYER                                 │
        │  runs with negative controls, writes nothing │ → structured acceptance report
        │  report lands in notes/_endstate/audits/     │   (the only thing intent may read)
        └─────────────────────────────────────────────┘
```

Supporting cast: `criteria-gate` (rules may not be *invented* inside task books — every rule must trace to a human-authored source file), `knowledge-gate`, `endstate-loop` (gap measurer + accumulating ledger), `endstate-view` / `executor-view` (observability panels; the endstate panel edits state via a real tool call, **without waking the model**).

### Key design decisions

1. **Capability-level > prompt-level.** `read`/`glob`/`grep`/`pwsh`/`bash` are *removed from the intent layer's tool table* — verified on the real `ToolRuntime`: intent sees 4 tools, executor sees 11. Not "please don't look" — the eyes are not installed.
2. **Fail-loud, name by name.** `tools.restrict()` throws on unknown tool names; one bad name would silently leave the whole mask unapplied. So masks are dispatched **per name**, and any "exists but not removed" case raises a warning.
3. **Default-frozen executor with budget leases.** Permission = `tool × scope × quota`, granted per task. Exhaustion is a *correct stop*, not laziness. The gate's own source can never be leased; three constraint challenges → circuit break.
4. **State criteria, zero tokens.** Goal continuation is judged by a host-side state machine (0 tokens per check), versus the market's pattern of replaying logs to a judge model (one LLM call *per turn*).
5. **Negative controls everywhere.** Preflight gate, smoke tests — every check embeds a probe that *must go red*; if the counterexample stays green, the whole verdict is untrustworthy.
6. **Postmortem-driven rules.** `apply()` never throws (learned 2026-09-15 when one throwing plugin made the entire window unlaunchable). Every incident became a tool or a law.

### Honest boundaries

- Tool-schema isolation is **not** a filesystem sandbox. The intent layer can still *dispatch* a subagent to look — it reads a report instead of crawling the site itself. True read-only needs OS-level mounts, which is out of scope here.
- The second guard layer (`judgeCleanRoom`) is explicitly labeled **heuristic** — it catches "casual peeking", not a determined bypass. The capability layer above it is not heuristic.
- The harness APIs these plugins hook are pre-1.0 and will drift; the *ideas* (negative controls, budget leases, capability isolation) are not tied to DSH.
- **Model-agnostic by necessity.** The harness accepts multiple model providers, and every failure class fixed here — pollution, false completion, upward contamination — is model-independent. A weak bundled model doesn't undermine this layer; it makes the guardrails *more* necessary. The worse the model, the more valuable capability-level isolation becomes.

## Engineering discipline

- **`preflight-dsh.mjs`** — predicts "will the desktop still launch?" *before* restart, with a built-in negative control. Exit codes: 0 green / 1 won't-open (with cause) / 2 missing deps.
- **`verify-all.mjs`** — the master gate: patch YAML, real profile composition, fallback home, linked plugins, `app.asar` integrity, snapshot health.
- **`snapshot.mjs` + rollback scripts** — one command back to a known-good state.
- **Semantic exit codes** — `smoke.mjs`: 0 pass / 1 assertion failed / 2 missing deps (never disguised as a failure).

## Market comparison

A mechanism-level comparison against **601 plugins** from the official `awesome-dsh-plugin` list (`docs/市场对照分析.md`). One example: vs. `dsh-loop-continue` — that plugin resumes an agent turn that stopped mid-narration (intra-turn, one LLM judge call per check); my `executor-loop` answers a different question — *does the goal survive session compression and process restarts* (cross-session, 0 tokens). Both can coexist. The exercise also caught **two of my own recommendations that were wrong** (single-plugin framing applied to an architecture-level question); they are withdrawn in the document, with reasons.

## Evidence

- Intent layer tool table (real `ToolRuntime`): `subagent, dispatch_audit, read_compass, list_compass` — 4 tools. Execution layer: 11.
- Incidents survived: intent-guard once locked *all* sessions; executor-loop's hand-written `Config` once bricked the desktop. Both became regression tests.
- Regression suite runs real `Context`, real `apply`, real tool names extracted from `app.asar` — no mocks, no reimplemented logic.
